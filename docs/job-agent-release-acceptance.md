## 必须由用户参与的剩余门禁

每个平台分别完成；两边不能相互代替。

1. 在 Chrome 扩展管理页确认已加载的实际版本，并刷新本地工作台。仅回复“已更新”不算版本与流程验证。
2. 用户打开招聘平台、处理登录或验证码；选少量岗位核对采集的身份、标题及 JD。
3. 用户主动导出并预览脱敏 Fixture。当前库中的合成样本不能冒充当天真实页面样本。
4. 指定一个待确认岗位，核对最终话术；在受控验收流程中由用户明确确认一次真实投递。
5. 核对页面成功证据、同一 requestKey 的 Attempt / 时间线。已有 UNKNOWN 只读对账，不重投。
6. 将日期、commit、扩展版本、平台、证据和 PASS / FAIL 写入验收记录。不要记录 Cookie、令牌、聊天正文或账号资料。

## 回滚与后续使用

每轮独立 PR，优先关闭对应功能并回退代码；新增表、列和业务事实保留。存在新版本执行状态或历史数据时，旧二进制不得恢复写入破坏约束，优先前滚修复。严禁把旧数据库直接覆盖到新业务数据上。

反馈统计初期缺少可信历史样本是正常现象：继续记录真实反馈与观察截止时间，不为凑样本重复调用 AI 或补造历史。面试、Offer、拒绝等模型分类仍需用户确认成业务事实，策略采用不等于投递授权。
