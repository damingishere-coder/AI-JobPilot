# BOSS 投递与双平台持续采集（扩展 1.8.0）

## 行为变化

- 投递先检查实际站点权限、页面加载、目标岗位和内容脚本版本。发送前失败是 `PRE_ACTION_ERROR / NOT_SENT`；发送后结果失联仍为 `UNKNOWN`，暂停且不自动重发。
- 单关键词目标按新岗位的持久入队回执计数；历史岗位、跨关键词重复、详情不足和永久拒绝均不占名额。AI 分析结果不改变采集数量。
- 优先定位岗位列表滚动容器，比较岗位身份变化。普通下滚无新增后，最多执行三次上滚半屏再下滚恢复；每次等待新卡片最多 5 秒。新卡片即使历史重复也证明列表仍前进。
- 每关键词主动采集预算 15 分钟。详情导航计入；队列等待、明确人工暂停不计入。明确官网无更多才标记耗尽，恢复无进展或时间上限标记未完成并转下一词。
- 详情失败和提交拒绝后继续补采。队列满或数据库暂忙保留岗位等待；永久失败记录原因并继续。
- 断点保留入队归属、逐项回执、待提交详情、已见岗位、关键词和列表进度。继续未完成关键词沿用原批次，显式解除采集停止标记，不重试历史未知投递或未知 AI 调用。
- 前端按平台及档案保存结果，刷新后仍显示原因；旧结果缺少结束原因时显示原因未记录。

## 数据与版本

新增 Flyway V20 `fresh_scan_receipt` 表，未改写历史岗位及投递审计。主键为档案、平台、扫描批次、岗位身份，记住首次归属关键词和入队确认。后台回执、扩展与页面脚本必须同时更新。

扩展版本：`1.8.0`。后台脚本与 BOSS / 智联内容脚本协议版本：`2026-09-10-continuous-scan`。不增加站点权限。构建文件更新不表示 Chrome 已重载。

## 发布与回滚

发布前确认现有 RunDock 6866 的运行目录、父进程和托管记录，备份应用产物及扩展。SQLite 用备份 API 生成一致性备份，不能只复制运行中的主数据库文件。只更新既有服务，不新增实例。

浏览器实际验收包括：重新加载现有 Chrome 扩展，刷新产品及平台页并核对三处版本；两平台各选历史重复较多的关键词，确认越过首批后新增入队。投递验收使用产品的话术预览确认入口，核对平台结果和审计记录；未经确认不发送真实 HR 消息。

回滚优先回退本次代码并重新构建、恢复上一版扩展；保留 V20 迁移及已经产生的业务数据。不得用发布前数据库备份覆盖发布后产生的新投递或分析记录。数据库备份仅用于迁移失败且尚无新业务写入时恢复。
