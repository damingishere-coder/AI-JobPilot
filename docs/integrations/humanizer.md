# HR 发送前文字润色

HR 草稿和岗位定制招呼语在生成最终文本前使用 [blader/humanizer](https://github.com/blader/humanizer) 的文体规则。模型仍使用现有 GPT-6.1 Sol 通路。

## 来源与许可

- 上游版本：3.1.0。
- 固定提交：`225a6f39ac85f76ee48dbad772ea4abe4ed6c9d8`。
- 原始 `SKILL.md` 和 MIT `LICENSE` 随应用保存在 `src/main/resources/humanizer/`。
- 不执行上游安装脚本，不依赖全局技能安装，运行时不从 GitHub 下载规则。

`HumanizerPolicy` 从原始技能提取全部26个模式的识别线索、定义与规则，排除示例经历和默认的多版本输出要求。应用使用技能的嵌入模式，只返回原业务 JSON Schema 中的最终正文。中文 HR 场景约束由应用叠加，优先保留可信事实、数字、范围符号、URL、条件与承诺。

## 接入位置

1. `HrReplyDraftService`：候选回复 → 内部润色 → 最终 `replyText` → 现有解析和完整对话/事实审核 → 草稿预览或托管发送。
2. `JobAiAnalysisService`：批量分析中的 `greeting` 和 BOSS 招呼语修复请求均在输出前润色，继续执行原 JD/简历证据、长度和作品链接校验。

润色与文本生成在同一次模型请求中完成，不新增模型调用或写入阶段。已经预览确认的消息、人工编辑稿及历史发送记录不会在发送按钮之后被重新润色。婉拒固定回复“好的，谢谢”和无需回复的空正文保留。

润色规则版本纳入分析上下文版本，避免重新分析时复用旧文体请求。历史已完成结果保留；旧版本待执行分析需要用户显式重新分析。部署前确认分析队列已空。

## 验证与回滚

执行 `gradlew.bat test` 和 `gradlew.bat bootJar`。规则加载测试检查固定上游文件的摘要、26个模式、提示词预算和示例排除；HR/招呼语生成测试检查规则实际进入模型请求且原 Schema、事实、审核和回执边界保留。

可以回滚本次提交并通过既有 RunDock 服务重新部署，不需要回退数据库。不要用旧数据库覆盖更新后产生的岗位、草稿或发送记录。
