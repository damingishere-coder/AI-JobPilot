# P1.3：真实反馈与会话关联

V24 只新增 `opportunity_conversation` 和采集事件触发器，复用 Opportunity Event、HR 会话/消息、现有加密密钥与保留期。不增加自动聊天、QQ 发送或额外 AI 调用。

## 确认边界

现有 `HrAssistantStore.findJobKey` 使用 HR 身份或公司/岗位名称匹配；`ChatSession` 没有可靠岗位 ID。因此本轮**不自动关联**，旧 `job_key` 只作候选，用户在机会详情里明确选择。保留一会话多机会关联，取消关联可恢复；同一会话有多个有效关联时不自动把新消息分给任何机会。

唯一用户确认关联的会话收到新入站消息时，只追加 `HR_INBOUND_OBSERVED`，不推进阶段、不判断招聘结果。事件保存会话 ID 和需确认标记，不保存正文/姓名/平台 UID。重复消息指纹即使正文过期后再次采集，也不产生重复观察事件。

用户可以确认回复、继续沟通、电话、面试邀请、Offer、淘汰、退出，并可核对“截至某时暂未回复”。未回复观察需要指定 CONFIRMED Attempt 与截止时间；没有检查过不等于未回复，UNKNOWN 不能作为有效投递。未来时间和早于已知投递结果的归因被拒绝。收到面试邀请不创建已安排面试；后续 P1.5 单独处理轮次和时间。

反馈采用版本 CAS、请求摘要及幂等键。已知结果更正沿用机会详情的选择原事件/填写原因流程。发生时间不确定留空；备注加密。分析简历与实际投递简历区分，后者只有用户核实并指定同档案版本时才记录，并保存为用户报告，不从 AI 输入自动推断。

## 采集与保留期

未来新入队任务和新采集回执共同记录搜索发现来源，同一平台/批次/岗位只记一次首次关键词。历史关键词不猜测回填。

原 HR 正文清理继续运行，关联和已确认业务事件保留；不会把完整消息复制到长期事件。界面主动加载当前档案最近 100 个会话，只有确认关联后才允许读取最近 50 条保留期内消息。当前不回填旧分类、不批量扫描账号；较老会话分页和稳定岗位 ID 直接关联留待实际采集协议提供证据后增加。

## 测试与发布

自动化覆盖：名称匹配仅作候选、一 HR 多岗位、重复回调、跨档案拒绝、正文清理后历史/去重保留、未回复观察门禁、未来时间、首次关键词去重、档案删除顺序；前端确认才写入、默认实际简历未知、无副作用发送。另跑全量 Java/前端、静态构建、Chromium、真实 SQLite 一致性备份副本迁移演练。

本地人工验收用虚构会话和机会：关联两个岗位，模拟入站消息，确认只有用户指定机会推进；取消关联后无法再通过该机会读取消息；记录错误结果后追加更正。真实档案发布验收只查看界面，不修改真实求职结果。

回退关闭反馈入口，保留 V24 表及已确认事件。旧 HR 助手发送链不变；旧版本不理解新增关联的档案删除路径不能恢复使用，需前滚修复。禁止回滚数据库覆盖新业务事实。
